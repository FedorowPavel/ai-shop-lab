## Цель

Оркестратор открывает страницу логина, вводит `admin` / `1234` и попадает на главную-заглушку. Пользователь лежит в PostgreSQL, в DBeaver видна одна строка. Неверный пароль на главную не пускает.

## Вне скоупа

- OAuth, JWT, роли, регистрация, восстановление пароля.
- Каталог, корзина, Pexels, RAG и расширение `vector`.
- Защита всех будущих страниц магазина. На этом шаге проверяем только логин и главную-заглушку.
- Отдельный сервер Postgres на Mac. База — контейнер из `docker-compose.yml`.

## Критерии приёмки

- [ ] Страница логина на Next.js (App Router): поля логин и пароль, простая форма без макета «как в магазине».
- [ ] В PostgreSQL есть таблица пользователей и ровно одна строка: логин `admin`. Пароль `1234` в ячейке не лежит открытым текстом, лежит хеш.
- [ ] Верные `admin` / `1234`: backend проверяет хеш, ставит простую httpOnly cookie-сессию (это не JWT) и браузер открывает главную-заглушку, где видно, что вошёл `admin`.
- [ ] Неверный пароль или пустые поля: остаёмся на логине, сессии нет, текст ошибки виден.
- [ ] Главная без cookie не выглядит как успешный вход: есть переход на логин, имени `admin` нет.
- [ ] Повторный запуск миграции не создаёт второго `admin`.
- [ ] `npm test` и `npm run typecheck` в `backend/` и `frontend/` зелёные.
- [ ] В `docs/db-schema.md` записано, зачем эта миграция и зачем уникальность логина.

## Что проверить руками

1. `docker compose up -d`, применить миграции. В DBeaver (`localhost:5432`, база `shop`, пользователь `shop`, пароль `shop`) открыть таблицу пользователей: одна строка `admin`, в колонке пароля не текст `1234`.
2. Открыть страницу логина, ввести `admin` / `1234`. Открывается главная, на ней видно `admin`.
3. Выйти из сессии (очистить cookie или кнопка «выйти», если она есть на заглушке) и ввести `admin` / `0000`. Остаёмся на логине, главная без сессии не показывает вход.

## База данных

Миграция создаёт таблицу пользователей:

- идентификатор;
- логин, `NOT NULL`;
- хеш пароля, `NOT NULL`;
- время создания.

Уникальность логина — ограничение unique, а не проверка в коде. Под ним PostgreSQL строит уникальный индекс. Запрос логина ищет строку по равенству логина (`WHERE login = …`). Индекс этот поиск обслуживает, но при одной строке выигрыш по скорости ничтожен. Ограничение нужно из-за инварианта: два `admin` существовать не могут. Два одновременных INSERT с одним логином — один проходит, второй получает ошибку уникальности. Отдельный неуникальный индекс по логину не добавлять: он дублировал бы unique.

Хеш: в форме вводят `1234`, в базу пишется результат хеширования. Сравнение при логине — через функцию хеша, не через `password = '1234'`.

Транзакции на несколько таблиц здесь нет: одна таблица и одна строка-сид. Сид идемпотентный: повтор миграции не вставляет второго пользователя.

Расширение `vector` не включать.
