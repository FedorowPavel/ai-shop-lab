# Схема базы

База `shop` в контейнере Postgres 16. Расширение `vector` не включено.

## schema_migrations

Служебная таблица раннера, не предметная.

| Колонка | Зачем |
|---|---|
| `filename` | Имя файла миграции, первичный ключ |
| `applied_at` | Когда файл применился |

Раннер при старте backend смотрит сюда и не выполняет файл второй раз. Иначе повторный `CREATE TABLE users` упал бы, а сид мог бы пытаться вставить ещё одного `admin`.

Каждый новый SQL-файл выполняется в транзакции вместе с `INSERT` в `schema_migrations`. Упала миграция — откатились и файл, и отметка. Это не бизнес-транзакция магазина: она не даёт пометить миграцию применённой, если SQL оборвался на середине.

## users

Миграция `backend/migrations/001_users.sql`.

| Колонка | Зачем |
|---|---|
| `id` | `uuid`, ключ строки. Его кладём в подписанную cookie сессии |
| `login` | `text NOT NULL`. Учётка, которую вводят в форме |
| `password_hash` | `text NOT NULL`. Хеш bcrypt, не пароль |
| `created_at` | Когда строка появилась |

Сид один: `login = admin`. В `password_hash` лежит bcrypt-хеш пароля `1234` (cost 10). Повторный `INSERT` того же логина делает `ON CONFLICT (login) DO NOTHING`, поэтому даже прямой повтор SQL не создаёт второго admin.

### Почему unique, а не отдельный индекс

Ограничение `UNIQUE (login)` называет индекс `users_login_unique`. Запрос логина — `WHERE login = $1`. Индекс этот поиск обслуживает.

При одной строке выигрыш по времени ничтожен. Ограничение нужно из-за инварианта: два `admin` существовать не могут. Два одновременных `INSERT` с одним логином — один проходит, второй получает код Postgres `23505`. Отдельный неуникальный индекс по `login` не добавляем: он дублировал бы unique и только замедлял бы запись.

Пароль в запросе не сравниваем (`WHERE password = '1234'` нет). Строку находим по логину, хеш проверяет `bcrypt.compare` в приложении.
