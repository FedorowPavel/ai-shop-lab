# Review code

Ревью для обучения, не для придирок к стилю. Пользователь читает код и должен уметь пересказать его.

## Порядок

1. Прочитать задачу в `tasks/`, которую закрывает diff. Сверить diff с критериями приёмки и блоком «вне скоупа».
2. Смотреть diff целиком (`git diff` или `gh pr diff`), не отдельные файлы в отрыве от задачи.
3. Прогнать тесты и typecheck, если ревью локальное и команды ещё не гонялись в этом заходе.

## На что смотреть

- Поведение совпадает с критериями приёмки.
- Ошибки и пустые состояния не молчат: неверный пароль, пустой список, недоступная БД.
- Секреты не закоммичены. Pexels-ключ не уезжает в браузер.
- Тест покрывает новое поведение, а не только «файл импортируется».
- База: миграция обратима насколько это дёшево; индекс совпадает с реальным фильтром или сортировкой; транзакция держит инварианты, которые нельзя нарушить двумя запросами; кэш имеет правило инвалидации; параллельные запросы не теряют обновление без явной стратегии.

## Формат ответа

- **Приёмка:** выполнено или нет, по пунктам критериев.
- **Разобрать:** участок, который оркестратору стоит пересказать своими словами. Для каждого — что делает, почему так, какой вопрос задать себе.
- **БД:** почему эта миграция / этот индекс / эта транзакция. Если объяснения нет в `docs/db-schema.md` — сказать об этом.
- **Блокеры:** что чинить до merge. Нет блокеров — так и написать.

Не переписывать код во время ревью, пока пользователь не попросит исправить.
