# Implement task

Код писать только после «подтверждаю» по конкретной задаче.

## Шаги

1. Прочитать `tasks/NNN-*.md` целиком. Критерии приёмки — это спецификация. Вне скоупа не делать.
2. Убедиться, что рабочее дерево не смешивает чужие незакоммиченные правки. Если смешивает — остановиться и спросить.
3. Обновить `master` (`git checkout master`, затем `git pull`, если есть remote). Ветка задачи: `feature/task-NNN` (только номер, без суффикса названия). Создать от актуального `master` и переключиться на неё.
4. Если `master` ещё нет (репозиторий без коммитов) — остановиться. Сначала нужен коммит каркаса на `master`.
5. Реализовать задачу. UI простой. Секреты только в `.env`, не в git. Ключ Pexels не попадает в клиентский бандл.
6. База: каждая миграция, индекс, транзакция, кэш и блокировка — с объяснением «почему» в ответе пользователю и в `docs/db-schema.md`.
7. Пометить код, который трудно объяснить вслух (особенно SQL), и кратко разобрать его в ответе.
8. Прогнать тесты и typecheck затронутых пакетов. Ожидаемые скрипты: `npm test` и `npm run typecheck` в `backend/` и `frontend/`. Скрипта нет — добавить минимальный и не пропускать проверку. Нет теста на новое поведение — добавить минимальный. Падать — чинить и гонять снова.
9. Перед push выполнить навык `update-docs`.
10. Закоммитить (сообщение — зачем изменение). Push feature-ветки. Pull Request в `master` через `gh pr create`. В теле PR: что сделано, как проверено, объяснение изменений БД если они были. Вернуть URL PR.
11. В файле задачи выставить статус `in-review` и номер PR.

## Не делать

- Не пушить в `master` напрямую.
- Не открывать PR при красных тестах или typecheck.
- Не начинать следующую задачу в той же ветке.
